# DeckSmith · 实战派演示生成

> 你拿到的不是模板库，是**设计逻辑 + 渲染积木**。每份材料形式不同，你要为它**设计适配的框架**，而不是套一个固定样子。
> HTML 端有现成渲染器（填 plan JSON 即出）；PPT 端给你视觉积木（pptx_toolkit），用下面的逻辑**为这份材料现搭框架**。

## 这个 skill 的两端能力

| 输出 | 怎么生成 | 灵活度 |
|---|---|---|
| **HTML 演示**（scroll-snap 单页一屏 / 单页长卷） | 写 `plan JSON` → `deck_smith.html_renderer.render_from_files(preset, plan, out)` | 14 布局为起点，可选可组合；不够用时可自定义，不受限于这 14 种 |
| **PPT**（python-pptx 原生可编辑形状） | 用 `deck_smith.pptx_toolkit` 积木（渐变/阴影/文字渐变/形状/字体/溢出预检）**按本逻辑现搭脚本** | 完全自由，逐页为内容设计 |

→ HTML 适合「演示/投屏/发链接」；PPT 适合「可编辑/塞进 Word 合集/企业标准格式」。形态选择见 Step 0。

> 🔴 **布局是积木，不是枷锁**：这 14 种是经实战验证的高质量**起点**。当一份材料的信息结构用这 14 种都覆盖不好时——**不要硬塞进最接近的那个**，而是改造它的结构、组合多种、或为这份材料**新写一个布局**（HTML 端在 `html_renderer.py` 加一个 `render_slide_xxx` 函数；PPT 端用 pptx_toolkit 积木自由搭）。**逻辑凌驾于样子之上：先按 Step 3 判断这份材料该是什么框架，再决定用现成布局还是自定义——绝不为迁就布局牺牲表达。**

# 核心工作流：材料 → 演示

**铁律：先理解材料、再设计框架、最后才渲染。不要拿到内容就开始填字。**

## Step 0 · 确定输出形态

| 用户说 | 形态 |
|---|---|
| 演示 / 投屏 / PPT / 一页一屏 | 分页（HTML scroll-snap 或 PPTX） |
| 让领导一眼看完 / 拖着看 / 不分页 / 发链接 | 单页长卷 HTML |
| Word 版 / 要打印 / 塞进材料合集 | Word（本 skill 不覆盖，提示用 python-docx） |

说不清就**问用户**，不要默认 PPT。

## Step 1 · 语境识别（决定整体基调）

| 语境 | 角色 | 适配布局族 |
|---|---|---|
| **议题型**（向上级/平级提诉求） | "恳请支持" | icon-duo / compare-table / dual-path / tier |
| **工作汇报型**（汇报成果） | "已完成 / 在做 / 计划" | dashboard / progress-cards / chart-duo / milestone |
| **应答型**（领导问你答） | 左口播 + 右备问 Q&A | 双栏段落，不用 bullet |

先问自己「这是给谁看 → 他想拿到什么」。议题型塞进度条、汇报型用诉求口吻 = 错位。

## Step 2 · 内容提炼：业务角度，不是周报角度

汇报型材料最大的坑是把"做了什么动作"当"达成了什么"。

| ❌ 周报角度（过程动作） | ✅ 业务角度（实质成果） |
|---|---|
| 完成 X 材料整理 | 通过 X 同步 Y 进展 / 形成 Z 共识 |
| 明确三大诉求 | 就 X/Y/Z 与对方开展一轮沟通 |
| 完成需求梳理 | 推动 X 立项 / 启动开发 |

触发词警觉：完成材料 / 明确 / 围绕 / 梳理 / 形成 → 多半是周报角度，重写成实质。
（年终/述职/高层汇报适用；周报/status update 不适用。）

**同时过滤内容**：创新型/有亮点的 → 详写成页；日常机制（每天都做的）→ 不报；数据型成果 → 图表化。

## 🔴🔴 Step 2.5 · 图片策略（排版之前必须定，最易被忽略）

**核心铁律：绝不为不存在的图片留空位。** 在排架构、选布局**之前**，先确定这份材料的图片来源——三选一：

| 情况 | 做法 |
|---|---|
| **A. 有业务图片**（用户提供了真实图/截图/产品图） | 按"有图"规划：用 image-text(有图) / product-gallery / progress-cards(带图)，图为内容服务 |
| **B. 无图、但有生成条件且内容需要**（装了生图工具 + 有场景图/产品图需求，见「配图增强」） | **先规划要生成哪些图（列清单 + prompt）→ 生成 → 再按生成的图设计版面**。绝不先留位再补图 |
| **C. 只有文字素材**（无图、不生成 —— 最常见） | **走「文字 + 设计」路线**：用形状 / 色块 / 渐变 / 分隔线 / 图标 / 大数字 / 数据可视化来组织和填满页面（像优秀 HTML 那样靠**设计**而非图片撑场面） |

**这个决策直接决定 Step 4 选什么布局**：
- **C 情况（纯文字）只用靠形状/排版就成立的布局**：dashboard / tier / timeline / compare-table / icon-duo / dual-path / split-layout。
- **C 情况严禁用图片驱动布局**：progress-cards(带图版) / image-text(带图) / product-gallery —— 它们没图就会留白。
- 若内容必须用某个默认含图区的布局，要么换布局，要么**用设计元素（色块/图标/大数字/引用）填满图区**——绝不留空等图。
- **例外**：用户明确要求"留图位待补"时才留。

## Step 3 · 信息架构：先判断逻辑关系，再选结构

🔴 **设计顺序铁律**：先判断信息之间是什么关系，选定视觉结构，再把文字填进结构槽位。**反了就会退回"堆文字调字号"。**

| 信息关系 | 该用的结构 | ❌ 别用 |
|---|---|---|
| 对比 / 差异 | compare-table / 双栏 / 雷达 | — |
| 递进 / 演进（A→B→C） | timeline / tier-diagram | — |
| 并列同级 | KPI 网格 / 卡片网格 | 强行差异化版式 |
| 分层 / 优先级 | 金字塔 / 漏斗 / 阶梯 | — |
| **关系**（A 来自/属于/流向 B） | **节点-连线 graph**（SVG/ECharts） | matrix/表格 |
| 现状 → 目标 | 左右双栏 + 中间转向条（X→Y） | — |
| 数据成果 | 图表（柱/饼/折线）+ KPI 条 | 纯文字列表 |

**内容密度上限**（超出立刻分页，不挤不滚）：标题页 1 标题+1 副标；内容页 1 标题+4-6 点；卡片网格 ≤6 卡。

## Step 4 · 逐页布局：内容性格 → 视觉语言

每页用「1 个动词/名词」概括它本质在表达什么 = 这页的性格，按性格选视觉语言：

| 内容性格 | 适配版式 |
|---|---|
| 结构性问题 / 层级 | 金字塔 / 漏斗 / 阶梯 |
| 具象产品 / 案例集 | 产品矩阵（图卡+数据+短文） |
| 情感叙事 / 服务温度 | 大场景图 + overlay 文字 |
| 系统能力 / 平台架构 | 合作矩阵 + 能力图 |
| 流程链条 / 因果递进 | 叙事 stepper（顶部步骤条+长卡+桥接箭头） |
| 对比反转 / 现状→目标 | 左右双栏 + 中间转向 |
| 数据横向对比 | KPI 网格 / 柱形图 |

**多章节材料防同质化（章节 3-5 个且性格差异大时用）**：保留页眉/理念条/收尾条统一（给节奏），中段主战场性格化（给记忆点）。
**何时不要性格化**：并列同级 / 严肃路演 / 章节≥6 / 时间紧 → 统一版式反而对。

## Step 5 · 配色

- **省心**：从 8 套预设选（`presets/`）：暗黑高端（warm-gold-dark）/ 亮色互联网（blue-orange-light）/ 科技（ink-gradient）/ 莫兰迪（morandi-grey）/ 教育亲子（forest-cream）等。按场景调性匹配 axes（tone 基调 / hue 色相 / saturation / contrast）。
- **定制**：从品牌色推导 → 见 `references/color-guide.md`。
- **大屏放映**：字号分级放大（正文 +25% / 标题 +15% / 大字 +10%），见 `references/chinese-pitfalls.md`。

## Step 6 · 渲染

- **HTML**：优先用 14 布局写 `plan JSON`（结构见 `references/plan-schema.md`）→ `render_from_files(preset_path, plan_path, output_path)`。**若现有布局都不贴合这份材料的结构，就在 `html_renderer.py` 加一个 `render_slide_xxx` 函数自定义布局，再在 plan 里引用**——见上方「布局是积木，不是枷锁」。
- **PPT**：用 `pptx_toolkit` 积木为每页写布局代码。字体走 `set_run_font`（默认微软雅黑 + ≥12pt，三套 typeface 防回退）。渐变/阴影/文字渐变是必做的质感来源，不要交付纯色块。

## Step 7 · 自检（交付前必走，不偷懒）

1. **内容完整性**：原文的重点工作/行动项/决策点，每项是否有**独立卡片或段落**？不能被产品图/架构图"视觉化替代"。汇报领导问"重点几项"必须能从材料直接读出。
2. **无图不留白**（最易翻车）：页面有没有为"不存在的图片"留的空位？有 = 违规 → 换纯文字设计布局，或用形状/色块/大数字/图标填满（见 Step 2.5「图片策略 C」）。**没有图片素材时，设计绝不主动留图位。**
2. **文本溢出**（中文刚需）：
   - PPT：用 `pptx_toolkit.audit_text_boxes()` 审计长 desc，有 `[BAD]` 不交付。
   - HTML：三层检测——bbox + `scrollHeight-clientHeight` + footer 重叠，任一 >阈值都要修。
   - 🔴 playwright 通过 ≠ 视觉通过：headless 与真实浏览器渲染有差异，CSS 收紧时留 60-100px buffer，内容控制在视口 90%。
3. **总结页不重复**：总结页内容若 ≥70% 能在前文找到 = 重写。用「单一数字目标 + 外部对照 + 学习姿态」三件套。
4. **不编进度**：未启动事项不给进度条；不确定的事用"沟通推进/协调/探索"，别说死。
5. **措辞归属**：自己主导=完成/落地；别人主导=配合/协同。

# 配图增强（可选 · 预留接口）

> ⚠️ **当前版本不含生图工具**——本节是预留的编排逻辑设计。DeckSmith 本体不生图；无图场景一律走 Step 2.5「图片策略 C」（纯文字 + 设计填充）。以下描述的是"若未来接入兼容的生图工具应如何编排"。

如果用户**额外安装了兼容的生图工具**（浏览器自动化，调 Gemini/ChatGPT 网页版），可在生成演示后为它配图：

**判断**：演示里有「场景图/产品图/情感叙事页」需要配图，且用户已装 `deck-image-gen` 且已登录浏览器账号 → 走「图片策略 B」（先规划要生成的图 → 生成 → 按图设计）。否则走「图片策略 C」（纯文字 + 形状/排版设计，**不留任何图位**）。

**调用逻辑**（详见 `references/image-gen-bridge.md`）：
1. 从演示内容**提炼生图 prompt**（每张图一句具象描述，风格与演示调性一致）
2. 调 `deck-image-gen` 的 `/api/generate`（POST `{prompts:[...], prefix, mode:"image"}`）→ 图片落盘
3. 把生成的图**回填**进 plan JSON 的图片位 / PPT 的 `add_image()`，重新渲染

> ⚠️ 生图工具需要：装 Google Chrome + 登录 Google/ChatGPT 网页版（用网页版额度，非 API key）。未装则跳过，不报错。
